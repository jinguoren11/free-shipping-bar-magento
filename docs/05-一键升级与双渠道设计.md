# 一键升级 + 双渠道（Marketplace 版 / 官网下载版）设计

> 老任铁规矩：每个插件必须能一键升级，让小白也能用；第一次手动装，之后每个新版本一键升级。
> 老任决定（对话中直接给出，待总管记入 OWNER-DECISIONS.md）：A 选 2；**下载分流（最新版，取代之前的"主下载放官网"）**：
> 主下载 = **GitHub Releases**（每个版本附 zip）；官网只放说明/下载页，下载按钮直接指向 Releases 里 zip 的下载地址，**官网不另存 zip**；一键升级读 **GitHub Releases 公开信息（结果缓存）**；引流写在 README 和 Releases 说明里（"更多功能见 GetDropFlow（getdropflow.com）"+ 请点星）；**仓库先保持私有，做好测试后由老任批准再公开（我不改可见性）**；Marketplace 版规则不变。
> 参考（只读，没改任何文件）：`jinguoren11/dropshipkit` 的 `Admin/Model/Upgrade`（约 60 个类）。我们的插件**没有数据库表**，所以砍掉数据库备份/还原、同步暂停、授权码，做精简版。

## 1. 两个渠道，同一份代码

| | **Marketplace 版** | **官网/GitHub 下载版（direct）** |
|---|---|---|
| 安装 | `composer require`（Adobe 官方渠道） | 第一次：下载 zip，解压到 `app/code/GetDropFlow/FreeShippingBar/`，执行 `setup:upgrade` |
| 升级 | 靠 Adobe 的更新（Composer / Marketplace 更新提示）。**用户手册写明** | 设置页"升级卡片"：点一下，自动备份→升级→出错自动退回 |
| 插件内自己下载代码 | **没有这个功能，代码里连这些文件都没有**（官方规则不允许；审核会扫代码） | 有 |
| "更多工具"面板默认 | **关**（老任批准 A=2） | 开 |

**怎么用一个开关区分渠道**：源码里只有一份。构建脚本 `build/package.sh --channel=marketplace|direct`（默认 direct）：
- `marketplace`：删除所有"仅 direct"文件（`Model/Upgrade/`、升级卡片 Block、`etc/adminhtml` 里升级分组、`etc/di.xml` 里升级部分，全部用 `CHANNEL:direct-begin/end` 注释或独立目录标记），把 `show_more_tools` 默认改 0，把 `Model/Channel.php` 的常量改成 `marketplace`；打包后**扫描确认无 curl/exec/proc_open/ZipArchive 等字样**才算成功。
- `direct`：全部保留。
- 两个包名：`getdropflow-module-free-shipping-bar-1.0.0-marketplace.zip` / `…-direct.zip`。

## 2. 升级的整体流程（direct 版）

**信息放哪**：GitHub Releases（`jinguoren11/free-shipping-bar-magento`），每个 Release 附 3 个文件（由 `build/release-assets.sh` 生成，**我只生成，不上传**）：
- `getdropflow-module-free-shipping-bar-<版本>-direct.zip`：升级包（升级卡片下载它）
- `free-shipping-bar-direct.zip`：同一文件的**固定名字**副本——官网下载按钮可以永远指向 `https://github.com/jinguoren11/free-shipping-bar-magento/releases/latest/download/free-shipping-bar-direct.zip`，浏览器直接下载，不用每次改官网
- `manifest.json`：**签名的版本信息**（版本号、zip 地址、sha256、字节数、最低可从哪个版本升级、三语更新说明、签名）

**升级卡片怎么取信息（"检查更新"按钮才联网）**：`GET https://api.github.com/repos/jinguoren11/free-shipping-bar-magento/releases/latest`（公开接口，不带任何商家数据，不用令牌）→ 找到附件 `manifest.json` → 下载 → 验签。结果用 Magento 缓存存 **6 小时**；按钮"重新检查"最少间隔 10 分钟（GitHub 匿名接口每 IP 每小时 60 次，不能每次都请求）。

**为什么还要签名**：GitHub 返回的内容不是我们签的，万一账号或附件被人动过，没有签名就会推送恶意代码。验证链：签名（私钥只在老任/总管手里，不进仓库）→ 版本号格式 → zip 地址必须以 `https://github.com/jinguoren11/free-shipping-bar-magento/releases/download/` 开头（别的仓库、仿冒域名、`..` 都拒绝，有单元测试）→ 下载后 sha256 和字节数一致 → 包内路径安全检查。任何一步不对 = 不升级、不动现有文件。

**⚠️ 仓库现在是私有的**：匿名访问不了私有仓库的 Releases，所以**一键升级在仓库公开之前无法对真实 GitHub 工作**，只能用"本地测试服务器"验证（测试时可配置另一个允许的地址前缀，仅限 127.0.0.1/localhost）。仓库公开由老任批准，我不改可见性。

**步骤（每步有"撤销"，失败按相反顺序全部退回，参考 GetDropFlow 的 UpgradeRunner）**
1. 预检：安装在 `app/code`（Composer 装的不支持，提示用 composer）、目录可写、能在后台运行命令（`bin/magento`、php 路径）、磁盘空间、无其他升级在跑（锁）、新版本比当前高、当前版本满足 `min_from`。**预检不过就把原因用大白话写在卡片上，并给手动升级步骤，不动任何东西。**
2. 下载并校验（见上）。
3. 备份：把旧插件目录**整个移走**到升级工作目录（不留在 app/code，避免被加载两次）。
4. 进维护模式（`maintenance:enable`，放行管理员 IP 以便看进度）。
5. 换新文件 → `setup:upgrade` →（生产模式）`setup:di:compile` + `setup:static-content:deploy` → `cache:flush`。
6. 验证：`module:status` 里模块已启用，且新目录里的版本号 = 目标版本。
7. 退出维护模式，删旧备份（保留一份最近备份供手动退回），状态写"完成"。
- **任一步失败/被中断**：换回旧目录 → 重跑 `setup:upgrade`/编译/静态文件 → 退出维护模式 → 状态写"已退回"，卡片显示原因。退不回去时：保持维护模式 + 卡片显示"需要人工处理"和恢复命令（宁可停站也不留半新半旧代码）。
- 在**独立后台进程**里跑（网页请求会超时），状态写入状态文件，卡片每几秒读一次显示进度；进程被杀的下次打开卡片时自动退回。

## 3. 设置页"升级卡片"（direct 版）
放在设置页靠上位置（不在"更多工具"里），小白能看懂：
- 当前版本；最新版本（点"检查更新"才联网；**不自动联网**，也没有定时任务）
- 有新版本：更新说明（取自 manifest.json）+ 绿色按钮"一键升级"；预检不过：灰色按钮 + 原因 + "手动升级"说明
- 升级中：进度（第几步/共几步）、请勿关闭；完成/已退回/需人工：结果和原因
- 三语（英/西/中）。
- **隐私**：只在点"检查更新"时向 getdropflow.com 取一个公开 JSON（GET，不带任何商家数据，不带版本以外的参数）。这一点写进用户手册和 README。

## 2026-11-18 ASUS 068 复测后的修订（实现已改）
- **状态机**：点击后写 `queued`（不是 `running`），后台进程自己的预检把 `queued` 当作"这就是我要做的任务"；`running` 才算"已有升级在运行"。再次点击在 `queued`/`running` 时被拒。`queued` 超过 30 秒没人接手 = `failed`（原因 `START_TIMEOUT`），不再卡在"第 0 步"。
- **状态 `failed` / `rolled_back`**：`failed` = 在动商城代码之前就失败（下载/校验码/解压/维护模式开关），不重建、不说"已恢复"；`rolled_back` = 动过代码（SwapStep/CommandsStep 已开始）并已退回、重建。判断靠标记接口 `ChangesShop`。
- **后台 PHP**：命令行进程用自己（`PHP_BINARY`）；网页进程找与网站同 major.minor 的 `phpX.Y` / `phpXY`，再才是版本校验通过的 `php`；找不到则预检原因 `PHP_NOT_FOUND`，不乱猜。
- **执行方式**：改用 Magento 的 `Shell` 服务（后台启动与所有 `bin/magento` 子命令），不再直接 `proc_open/exec`；文件操作集中在 `Step\Files`（带理由的 phpcs 豁免，仅下载版）。
- **恢复入口**：除卡片外，Magento cron 每分钟（`Cron/RecoverUpgrade`，仅下载版）、`getdropflow:fsb:upgrade --recover`（`--recover` 还能在"恢复没完成"后重试）、以及升级命令启动时先恢复死掉的旧升级。"进程已死"用状态文件里的 pid 判断（>30 秒且进程不在），不必等 1 小时；进程还活着的慢编译不会被误杀。恢复完成后清理 `new/`、`package.zip`。
- **卡片**：所有原因码和步骤名都有 en/es/zh 文字（单元测试从源码里扫码核对）；轮询用 `global: false`，维护模式的 503 不再冒出 Magento 的红色错误条，卡片显示"维护模式中，会自动继续"。
